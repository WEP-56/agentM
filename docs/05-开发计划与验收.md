# 开发计划与验收

本文保留最初调研阶段的实施计划。当前五个 Agent 的程序管理与基本入口已接通，最新结果见 [0.8.0 开发记录](13-OpenCode与DSH接入.md)，Codex 独立沙箱探针结果见 [0.6.0 记录](11-Codex程序管理与兼容性.md)；下表是验收目标，不代表所有目标均已完成。

## 当前开发顺序（2026-10-09 用户确认）

**最新进展**：用户已确认 0.9.1 测试无问题，下一阶段指定为四页职责调整、配置页内五类 Agent 包管理，以及真实引导流程。详细范围和执行入口见 [HANDOFF](HANDOFF.md)。以下三步保留为此前的阶段顺序，不应再据此停在等待测试或重新接入 Agent 的阶段。

1. 先接通剩余 OpenCode 和 DSH，完成固定安装、Web 入口、认证访问、启动/停止、返回重入与数据保留等基础生命周期。
2. 五个 Agent 接通后，由用户进行完整测试，再依据反馈集中修复和打磨。模型调用、真机与日常使用体验必须记录真实结果。
3. 用户完成完整测试与打磨后，再开始 CC Switch 相关的配置管理扩展、提供商适配和切换能力。

0.8.0 已完成 OpenCode TUI / WebUI 和 DSH WebUI 的基础接入及自动化回归，进入第 2 步的用户完整测试。用户于 2026-10-09 已反馈 Claude Code、Codex、Pi 实际登录测试无问题。已有 Claude 配置功能继续参与测试；新增 CC Switch 配置管理仍等待完整测试和打磨完成。下表是原始阶段框架，具体先后以上述最新约定为准。

协作分工：开发侧负责实现、构建、静态检查和有价值的自动化回归；需要真实应用内点击、交互体验或账号验证时，优先由用户操作。提供简短步骤、预期结果和需要反馈的信息，根据反馈继续修复，避免在已有自动化证据后反复代替用户进行界面点击。

## 1. 实施顺序与退出条件

| 阶段 | 工作 | 可检查交付物 | 退出条件 |
| --- | --- | --- | --- |
| P0 技术基线 | 按锁定提交取回完整 DSHA，独立包名与签名；核对用户已验证 APK 的版本/引擎 | 能构建的技术分支、资产锁、设备记录 | Ubuntu/proot、Node、bash、真实 PTY、原 DSH 流程可运行 |
| P1 React 预览 | 四个主页面、引导、终端/Web 连接页、MockGateway | 可操作的全部模拟场景 | 不同状态按钮正确；返回、错误、重试流程完整 |
| P2 原生桥 | Kotlin RuntimeFacade、Service 所有权、快照与事件 | 原生环境检测、真实安装进度、终端打开/返回 | React 重挂载不影响进程；任务幂等、代次与事件补偿正确 |
| P3 多 Agent | 保留 DSH，再逐个接 Claude/Codex/Pi，接 OpenCode Web | 固定版本 recipe、真实运行记录 | 每个 Agent 完成安装、启动、工具调用、停止、再次进入 |
| P4 配置与升级 | 独立 adapter、保格式写入、冲突、升级槽位、恢复 | 配置往返样本、失败回滚记录 | 用户字段和历史保留；未知 schema 拒绝写入 |

P0 与 P1 可以并行推进，但不因前端完成就跳过底层验证。这里描述工作流并行，不要求启动额外 AI 子代理。

## 2. 当前参考目录的使用方式

examples/DSHA 和 examples/cc-switch 已大幅裁剪，保留文件内容及清理前 SHA-256，没有完整 Git 历史和构建资产。仅用于查阅与抽取；需要实际运行时按[恢复说明](参考源码与恢复.md)在另一目录克隆精确提交。

不要为了让裁剪版通过构建而伪造缺失类、绕过资产哈希、删除失败的测试或跳过 RuntimeTrial。提取一个模块时把实际依赖与有意义的测试一起迁移到产品工程。

## 3. P0 必须验证的问题

| 问题 | 方法 | 决策 |
| --- | --- | --- |
| 用户的稳定 DSHA 是哪个版本/引擎 | 从用户设备的关于/环境信息记录；本轮尚未获取 | 与当前锁定源码差异较大时先重建基线，不猜默认引擎 |
| targetSdk 37 下 rootfs 命令能否执行 | 真实启动 bash、Node、npm、git、Python，记录 engine 与 loader | 失败需定位资产/loader/内核，不退回 targetSdk 28 掩盖问题 |
| 私有项目文件系统是否适合开发 | git init/status、软硬链接探测、npm 项目依赖、文件监控 | 默认私有存储，验证后才开放外部工作区 |
| PTY 是否完整 | test -t、stty、中文输入、交互式 CLI、resize、Ctrl-C、子进程退出 | 没有真实 PTY 不能发布 CLI 功能 |
| 多进程是否可管理 | 两种不同 Agent 同时运行，分别停止与返回 | 不允许按进程名/端口批量杀死 |
| 基础系统能否独立于 DSH | 不安装 DSH 的新环境仍执行 shell/工具链 | 新增基础 ready 判定，避免五 Agent 依附一个 DSH 安装状态 |
| 原生 Agent payload 是否兼容 | Linux arm64 固定版本安装与实际工具调用 | 不支持组合单独禁用；npm 成功不够 |

上述命令只在新建测试工作区执行。数据删除、进程强杀、坏插件等故障注入使用可丢弃测试实例，不对用户正式 DSHA 数据做试验。

## 4. 有意义的自动检查

| 模块 | 需要验证的性质 |
| --- | --- |
| 状态归约 | 旧 generation 不能覆盖新会话；事件重复幂等；序列缺口重新取快照 |
| 安装计划 | 空间含新旧版本、缓存与备份；取消后不能发布半包；哈希失败不执行 |
| 文件解压 | 拒绝路径越界和链接写入逃逸，保留合法 rootfs 权限与链接语义 |
| 配置 | JSON/JSONC/TOML 往返保留非托管字段；认证不串用；revision 冲突拒绝 |
| 事务 | 第二文件写失败、掉电中断、外部修改后回滚不覆盖新内容 |
| 进程 | PID 复用/身份不匹配时不发信号；停止未确认不能释放维护锁 |
| 包管理 | 升级现有安装渠道和路径；原生载荷缺失不能报已安装 |
| 桥 | 远程 frame/不允许 origin 不能访问管理能力；无通用 shell 方法；日志脱敏 |

参考源码保留相关测试作为用例依据，不把上游测试数量当成本轮已通过的结果。纯 UI 微调不要求添加只重复实现的单测。

## 5. 真机验收矩阵

首轮至少一台用户认可的主设备和另一台不同系统/厂商设备；记录型号、Android/API、内核、ABI、页大小、WebView、内存、镜像摘要和实际引擎。最低版本与 16 KB 页支持在有相应设备后才宣布完成。

| 场景 | 预期 |
| --- | --- |
| 新装离线环境 | 解压、自检完整；无 API key 仍可进入环境和终端 |
| 网络中断/换源 | 可恢复下载；不同资产不拼接；坏摘要不安装 |
| 首次拒绝权限 | 基础功能按能力运行，真实解释限制 |
| 五 Agent 单独运行 | 每项固定版本，至少一次模型回复和一次工作区工具调用 |
| 配置切换 | 新 session 使用正确配置；旧 session 的有效 revision 不伪造 |
| 外部修改配置 | 冲突可见，草稿不丢，非托管字段不损坏 |
| 返回、旋转、换主题 | PTY 与 Web 服务不重复启动，不丢用户输入 |
| 首选端口被占 | 使用实际备用端口，原占用进程仍在 |
| 手动停止 | 不被看门狗立即拉起，结束对应 guest 树 |
| 息屏/后台 30 分钟与长时运行 | 记录真实结果；丢失状态可恢复，不声称所有 OEM 永久保活 |
| 系统回收/强制停止后再开 | 核对进程与事务；CLI 命令不自动重放 |
| Agent 升级失败 | 老版本仍可启动，历史与配置保留 |
| 系统重装/恢复中断 | 启动进入恢复判断，不在未知数据根写空配置 |
| 普通 UI APK 升级 | 不重装 Linux，不清项目，不更换 DSH 数据协议 |
| DSH/OpenCode 页面 | 认证正确、上传/下载/返回可用、管理桥不可达 |

性能先测基线，再定产品目标。至少记录冷/热启动时长、安装耗时、峰值内存、存储增量和后台存活情况，不填写未测的速度提升倍数。
